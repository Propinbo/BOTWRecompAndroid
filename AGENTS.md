# BOTWRecompAndroid Mali Engineering Rules

## 1. Language & Owner Reporting Policy

- **Owner communication:** Communicate with the owner in **Russian** (chat replies, summaries, questions, and status updates). Always end status updates and task completion replies with a concrete recommended next step.
- **Owner report format (advanced enthusiast level):**
  - Keep clear explanations of the mechanics behind changes (render fixes, synchronization, caching, shaders, timings) and **all exact test and measurement numbers** (`FPS`, `1% low`, frametimes in ms, temperatures in `°C`, error/crash counters, test pass/fail status).
  - Use short technical terms and metrics (`FPS`, `1% low`, ms, `°C`, cache) plus readable names of scenes, threads, and modes.
  - Avoid raw long identifiers (function, variable, constant, struct, and shader-stage names) and commit/file hashes in owner-facing chat reports—describe what they do briefly in plain language instead (unless the owner explicitly asks for raw symbols or hashes). Do not bloat reports with long lists of test filenames or branch/PR numbers; provide a compact summary instead.
  - Present numbers compactly in a short bullet list or table without fluff, following a 3-part Russian structure for task/test reports:
    1. *Substance & mechanics* — what was changed/fixed and why it was needed.
    2. *Test & measurement numbers* — exact before/after metrics by scene/thread and overall verification status.
    3. *What to do next* — which build to install, which settings to configure, and what to check next (or concrete recommended next step when no build/test action applies).
  - Short clarifying questions or brief replies do not need forced empty sections, but still follow the plain-language no-raw-symbol-dump style.
- **Repository and artifacts:** Write all code, comments, commit messages, PR descriptions, workspace rules, skills, subagent definitions, and tracking/technical documentation (`AGENTS.md`, `MALI_STATUS.md`, `MALI_PLAN.md`, `MALI_PROGRESS.md`, `.mali/**/REPORT.md`) in **English**, preserving full exact SHAs, hashes, symbols, filenames, and PR/branch references there for reproducibility and upstream maintainer review.

## 2. Governance, Roles, and Delegation

- **Owner's role:** Define goals, priorities, requirements, and success criteria. Decide major scope changes and consequential product/architecture trade-offs.
- **Agent's role:** Act as an autonomous senior engineer and researcher. Own technical decisions, investigation, architecture, implementation, testing, debugging, and verification.
- **Delegation & command autonomy:** Execute all engineering commands autonomously without pausing for command-by-command confirmation—including local and remote Git operations (`git commit`, `git rebase`, `git push` to `origin`, branch updates, `main` fast-forwards to verified upstream releases, `mali-workspace` checkpoints), GitHub CLI (`gh pr`, `gh issue`), builds, ADB/device tests, and workspace maintenance. Ask the owner only when project goals or priorities are genuinely ambiguous, a consequential product trade-off arises, or physical human action on hardware is required.
- **Accountability:** Take full ownership of the technical outcome, not just the assigned task. Report exact results, evidence, commands, unresolved issues, and blockers without overstating confidence or extrapolating unverified behavior.

## 3. Repository Hygiene and Non-Negotiable Safety Invariants

### Git Remotes, Branch Isolation, and Upstream Build Files
- Push PR, evidence, and `mali-workspace` branches to `origin` (`Propinbo/BOTWRecompAndroid`), never directly to `upstream` (`mamcjr/BOTWRecompAndroid`). Use `--force-with-lease` (never blind `--force`) when updating rebased PR branches.
- Keep source edits isolated in `.mali/worktrees/<slug>`. Never merge `mali-workspace` into `main` or any PR branch, and never stage or commit `.agents/`, `.mali/`, `AGENTS.md`, `GEMINI.md`, or `MALI_*.md` into source or PR branches.
- Keep `tools/patches.py`, `GAMELIB_ID` (`runtime/gamelib.h`), version hooks, benchmark save-writing targets, and tracked `.gitignore` untouched in upstream PRs unless the task explicitly targets them (changing `GAMELIB_ID` invalidates cached `botwgame.so`).

### Intellectual Property and PR Cleanliness (`CONTRIBUTING.md`)
- Never commit, stage, or upload Nintendo assets (`Dump/`, `extracted/`, `generated*/`, Switch `.bfttf`/`.ttf` fonts, game data, or user saves) anywhere in Git history, PRs, or public issues.
- Keep `.git/info/exclude` active across root and linked worktrees so `.agents/`, `.mali/`, `AGENTS.md`, `GEMINI.md`, `MALI_*.md`, and `android/deps/{src,work,out}/` stay untracked and invisible to source diffs.

### Physical Device, Save, and Driver Rules
- **Primary vs. secondary hardware targets:**
  - **Primary (Daily Play & Performance R&D):** Rooted **AYN Odin 3** (`SM8750`, Snapdragon 8 Elite, Oryon `6+2` `0-5`/`6-7` L2-only CPU, Adreno 830 GPU, Mesa Turnip `Gen8 V39 Patched`, `1080p @ 120.00 Hz` AMOLED, targeting **Native `1080p` (`1920x1080`, `100%`, `1:1`) `40.00 FPS` Ultra + Low-Power (`< 6–7.5 W`) + `tu_autotune` GMEM R&D**; no `>100%` SSAA/bicubic and no custom Turnip builds).
  - **Protected Secondary (Non-Regression Tier):** Galaxy Tab S11 (`SM-X730`, Dimensity 9400+, Mali-G925 `r49p1`) and OnePlus 13 (`CPH2653`, Turnip-only). All shared changes must preserve 100% of validated Mali-G925 behavior behind clean vendor/capability gates.
- **Rooted ADB (`su -c`) telemetry boundary:** Odin 3 is rooted; use `su -c` strictly for read-only sysfs/proc/log/dmesg/simpleperf telemetry and scratch setup inside app-owned paths. Never modify `/system`, `/vendor`, `/boot`, SELinux policy, or real user data. Always execute GPU/CPU benchmarks on Odin 3 **strictly sequentially** (never overlap device workloads).
- **Save preservation:** Never run `adb uninstall com.botwrecomp.android`, `pm clear com.botwrecomp.android`, or any command that overwrites real user saves/settings. Before any task that launches the game on a device, verify or create a dated SHA-256 backup in `.mali/user-backup/<YYYY-MM-DD>/` (`backup.py` / `backup_odin3.py` and `*.sha256` manifests; `crash_diagnostics.xml` increments `boot_count` harmlessly on app launch).
- **Scratch isolation, intermediate rollback, and Final Sign-Off play-ready deployment:** Run intermediate diagnostic and A/B test sessions strictly on isolated scratch directories (`LARECOMP_SAVE_DIR`, `LARECOMP_SETTINGS`, `LARECOMP_DATA_ROOT`, keeping `mods_off` clean during stock baselines), install test APKs in-place via `adb install -r` (never uninstall), and restore stock between separate campaigns when returning the phone to baseline. **At Final Sign-Off on Odin 3**, install the winning signed APK directly (`adb install -r`), back up live INI/`shared_prefs` once to `.mali/user-backup/<YYYY-MM-DD>-pre-final-deploy/odin3/` and `botwrecompandroid.ini.bak`, auto-write optimal settings into the live INI while baking `SM8750`/Adreno 830 smart hardware defaults into C/Java (zero manual env vars/toggles required), clean scratch paths, verify `27/27` game saves (`0` SHA-256 diffs) + intact `Turnip Gen8 V39 Patched` & `2686+` shader caches, and run one live verification launch via the normal Android launcher intent.
- **Adreno Turnip-only rule:** Test on Adreno (`Odin 3`, `CPH2653`, or any Adreno 8xx device) **exclusively with Turnip** (`VK_DRIVER_ID_MESA_TURNIP`, `driver-id 18`, e.g., `Turnip_Gen8_V39_Patched` / `V38_Patched`), never stock Qualcomm, unless the owner explicitly requests comparing or testing stock Qualcomm. Ensure custom Turnip loading is active in scratch/test config and verify `driver-id 18` / Turnip in `[vk]` startup logs before accepting measurements.
- **Windows NTFS junctions:** Worktree `android/deps/out` directories are NTFS junctions (`ReparsePoint`) pointing to `root/android/deps/out`. Never recursively delete a worktree before unlinking its junctions via `cmd /c rmdir "<junction_path>"`.

## 4. Verification, Concurrency, and Mandatory Pre-PR Review

- **Proportional, situational verification:** Decide verification scope on the spot based on risk and complexity. Default to fast deterministic checks first (`python -B tools/test_*.py`, standalone C/Bionic tests `tools/test_*.c` & `tools/test_android_runtime.ps1`, compiler diagnostics, `git diff`, and `python -B -S .agents/scripts/workspace_check.py`).
- **Mandatory pre-PR multi-agent code review:** Before opening any upstream PR (`gh pr create`) or pushing a substantive code/rebase update to an open PR, always execute an independent multi-angle adversarial review of `<base>...HEAD` using 2–3 parallel `independent-verifier` subagents (`invoke_subagent`) — or a `run_workflow` fan-out (`type_name="self"` with strict read-only instructions) for wide multi-file changes. Resolve all `CRITICAL` and `MAJOR` findings (plus valid `MINOR` defects), re-run verification, and record the review in `.mali/<topic>/upstream-pr/CODE_REVIEW.md`. Never self-certify a PR diff solely from the authoring context.
- **Ad-hoc subagents & workflows:** Outside the mandatory pre-PR gate, use `research`, `independent-verifier`, or `run_workflow` only when they genuinely save time or reduce risk—such as isolating broad codebase/log searches or parallelizing independent scans (`Model="flash"` for simple high-fan-out scans). Never spawn subagents mechanically for routine edits, doc updates, or checks already proven by deterministic commands.
- **Honest evidence separation:** Explicitly separate host/mock tests, native Android Bionic unit runs, and physical-GPU in-game observations. Never claim an on-device fix or benchmark result without real device logs/captures.
- **Upstream maintainer (`mamcjr`) PR standards:** Follow the codified checklist in `.agents/skills/upstream-release-and-pr/SKILL.md` (Section 5) before opening/updating any upstream PR: keep each PR strictly single-concern; guarantee zero hot-path overhead and zero behavior change when a feature is off or on untested GPUs (gate risky defaults strictly to tested drivers like Mali `r49+` / Turnip + provide a `LARECOMP_*` env rollback); add `watchdog.h` (`WD_R_*`) markers to any new render-thread wait (never `usleep` on render thread); keep desktop `#ifdef __ANDROID__` defaults and all 11 `i18n_*.inc` locales in sync (no `#NNN` issue numbers in user-facing UI text); and attach **isolated evidence from the exact PR commit** (not a combined prototype): exact device/OS/driver/game-version (`1.9.0`) + startup/runtime log lines proving the new path actually executed, A/B metrics including `1% low`/GPU/render-thread (and `LARECOMP_LOG_POWER=1` off-charger when relevant), before/after screenshots for visual fixes, cold/warm/upgrade-invalidation checks for caches, stress triad (inventory cycles + in-place reboots + 30+ min flat-RSS run) for default/lifetime changes, and an explicit tested-vs-untested GPU matrix.

## 6. Mali-G925 (r49p1) Direct-Heap Engineering Notes

- **No vertex-stage atomics (`vertexPipelineStoresAndAtomics = 0`):** `Mali-G925` (`v1.r49p1-03bet0`) exposes `fragmentStoresAndAtomics = 1` and `vertexPipelineStoresAndAtomics = 0`. Gate any GPU-side tracking/bitmap SSBO (`GMemTouch`, binding `25`) strictly to fragment and compute stages (`FS+CS`), while keeping vertex bound VBO/IBO/SSBO reads covered by bound-range flushes.
- **Static/UBO-copy overwrite trap under periodic `mprotect` demotion:** Periodically re-protecting hot CPU-written pools (`mprotect(PROT_READ)`) triggers SIGSEGV fault storms and hot-list churn (`256–427` blocks, `196–398` faults/2s) because the game rewrites static/UBO-copy buffers with identical or CPU-only bytes each frame. Keep periodic demotion off by default (`LARECOMP_MALI_HOT_DEMOTE_FRAMES=0`).
- **8 KiB coherent `GMemTouch` bitmap + `CPU_ONLY_UNREAD` classification:** Use a non-coherent L1-cached read before conditional `0 -> 1` `atomicOr` (+ `early_fragment_tests` on eligible `uses_gmem` FS, isolated via `MW_TF_GMEM_TOUCH = 1u << 24`) to graduate unread `0x022` `HOT` blocks into `CPU_ONLY_UNREAD` after `12` steady frames (`skipped_draws == 0` and no active shader compiles), dropping active `hot_blks` to `9–13` (`0.4–0.6 MB`).
- **`O(1)` dirty-generation fast-path (`plat_wt_dirty_gen`):** Maintain an atomic generation counter across write-tracking faults/range clears/resets so submits with no new CPU writes skip scanning ~120k tracked pages, reducing `gmem flush` CPU time from `~99–137 ms/2s` to `~17–28 ms/2s` (`0.28–0.46 ms/frame`).

## 6B. Snapdragon 8 Elite / Adreno 830 (Turnip V39) Engineering Notes

- **Oryon `6+2` L2-only topology (zero L3 cache):** `cpu0..5` share one 12 MB L2 (`384–3532.8 MHz`, `cap=792`) and `cpu6..7` share a second 12 MB L2 (`1017.6–4320 MHz`, `cap=1024`), with no shared L3 cache (`index3` absent). Without pinning (`0-7`), render/game threads ping-pong across clusters (`prime_pct` `25%–89%`); isolate Guest Core 0 + Render/Present onto `cpu6..7`, hot Guest Cores 1..2 onto `cpu2..5`, and workers onto `cpu0..1`, while keeping `4+3+1` Mali topology untouched.
- **Native `1080p` (`1:1`) + Low-Power (`< 6–7.5 W`) & scope cuts:** `1440p` @ `40 FPS` drew `~17 W` (`77.2 °C`), so target **Native `1080p` (`100%` `1:1` bypass)** plus `16px`-aligned sub-native scales (`65%/68%/70%` and optional `85%` `1632x912` `SGSR1`); drop `>100%` SSAA/bicubic downsampling and drop custom Mesa Turnip builds. Always scale ADPF target duration dynamically to active FPS (`~21.5–22.5 ms` at 40 FPS, not `16.67 ms` 60 FPS).
- **`gpu_heap` cached (`0xf`) vs `transient ring` (`0x7`):** Turnip V39 exposes `VK_EXT_map_memory_placed`, placing `gpu_heap 3120 MB` at `340000000` on memory type 1 (`0xf`, `HOST_CACHED`), while `transient ring` allocates memory type 0 (`0x7`, WC). Keep CPU reads off `transient ring` and validate WC vs cached staging empirically at `1080p @ 40 FPS`.
- **`tu_autotune` GMEM vs `TU_DEBUG=gmem` pass-fragmentation trap:** Turnip `tu_autotune` selectively runs heavy passes in GMEM (`plateau` `1080p` default `14.50 ms` / `6.50 W` vs `TU_DEBUG=sysmem` `16.21 ms` / `8.77 W`). Never force global `TU_DEBUG=gmem` (`33.64–44.03 ms`, `~20 W` across `140–214` fragmented passes/frame); feed cleaner passes into `tu_autotune` via pass merging, `STORE_OP_NONE`, `VK_EXT_attachment_feedback_loop_layout`, and LRZ recovery.
- **Keep `IR3_SHADER_DEBUG=nouboopt` OFF on `a8xx` (regression check):** Unlike Adreno `840+`, `a830` renders shadows cleanly without `nouboopt`; forcing it bloats `cat6` loads `3.7–10.1x` (`+1.53 ms`, `+1.05 W`). Do not add custom `nouboopt` workarounds; preserve a unit regression check keeping `nouboopt` off on `a830`.
